# Release Process

## Versioning

Use semantic versioning for product releases. Database migrations are monotonic
and separately identified by Alembic revision. Scanner/tool changes must be
recorded even when the application version does not change.

## Required release evidence

1. Approved change scope and updated canonical backlog.
2. Backend, worker, shell and frontend checks appropriate to changed code.
3. Security gate, dependency review and secret scan.
4. Migration upgrade verification from the supported previous release.
5. OpenAPI diff reviewed for compatibility and authorization.
6. Worker capability/version snapshot and scanner image identity.
7. Backup created and restore rehearsal status recorded.
8. Deployment readiness, smoke workflow and rollback decision.
9. Documentation and changelog updated.

The GitHub release workflow is supporting automation, not a substitute for
these gates. Releases must not publish mutable `latest` as the sole deployment
identity; production should use digest-pinned images.

## Rollback

Application images can roll back to prior project tags. Database rollback is
not automatic. Prefer corrective forward migrations; restore an approved backup
when compatibility cannot be maintained. Scanner evidence generated by the
failed release remains immutable incident evidence unless retention policy
explicitly removes it.

## Patch cadence

- Critical exploited platform/scanner dependency: assess immediately.
- High severity reachable issue: prioritized patch release.
- Routine application and scanner pins: reviewed scheduled update.
- Nuclei templates: runtime refresh with source/commit provenance and rollback.
- Base images and operating-system packages: rebuild; do not rely on stale cache.

Renovate/Dependabot proposals require compatibility and license review. A
successful build alone does not prove scanner behavior is unchanged.
